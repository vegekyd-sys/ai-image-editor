- 调研时间：2026-11-06 23:26–23:55 CST（Asia/Taipei，`date +%F` = 2026-11-06）
- 方式：只读。代码静态检查 + 共享 Supabase 库只执行 SELECT（Management API，`read_only: true`）。未改数据，未部署 Worker 或应用。
- 结论先行：**没有大范围影响**。上线约 26 小时内，能确认由 206 导致的失败共 **4 次工具调用、4 个用户、4 个项目**，全部失败在提交供应商之前，**没有扣费，不需要退款**。其中 2 次 Agent 自己换新 URL 重试成功（重试成功后才正常扣费）。但 Retake 的**交付拼接阶段**存在潜在资金风险（见第 5 节），建议尽快修。

## 1. 根因

`services/media-r2-cache/src/worker.mjs` 的 `serveR2()`：

```js
if (object.range) { ... return new Response(body, { status: 206, ... }) }
```

R2 的 `get()` / `head()` 在不带 range 时也会返回 `range` 字段，所以**所有命中 R2 层（`x-makaron-cache: HIT-R2`）的请求都回 206**，`content-range: bytes 0-(N-1)/N`，正文是完整对象。HEAD 也一样（项目 a814f253 的 Agent 在 run_code 里探测到 `HEAD=206 image/png 3357258`）。

是否命中 R2 层取决于时序，所以表现为**间歇性**：

| 情况 | 返回 |
|---|---|
| 对象还没进 R2（首次读） | `MISS`，透传 Supabase，200（后台回填 R2） |
| 本机房 60 秒内读过（`EDGE_TTL_SECONDS=60`，每个机房各自一份） | `HIT-EDGE`，200 |
| 已在 R2，但本机房 60 秒内没读过；或对象大于 512 MB 不进边缘缓存 | `HIT-R2`，**206** |

服务端（Vercel / Sandbox）与用户浏览器通常不在同一个 Cloudflare 机房，所以浏览器刚看过的媒体，服务端第一次读大概率是 HIT-R2 → 206。同一项目里短时间内连续读取会碰到 HIT-EDGE → 200，所以“刚失败、马上重试又成功”。

## 5. 潜在风险（尚未发生，但必须在修复里覆盖）

`video-retake.ts` 的 `assembling` 阶段在**供应商已经出片之后**用 `readProviderImage` 读 cdn 上的源视频、patch 和终帧图。源视频早已被读过并进了 R2，这一步大概率拿到 206，被 catch 后只返回 `Retake delivery is pending`，任务不会变成 `failed`，也不会触发 settle/退款，`reconcileVideoRetakes` 会反复重试。后果是：**供应商成本已花、用户看不到结果、积分停在预留状态**。目前库里没有这样的任务，是因为上线后能走到这一步的 Retake 只有 1 个（fe05388a，已完成）。612db792 一旦从 generating 往下走，在生产代码下有可能卡在 assembling。

## 6. 修复建议与上线顺序

两边都修，Worker 先上：

1. **Worker（根因，先上线）**：`serveR2()` 只在请求带合法 `Range` 时回 206。具体是 `if (rangeHeader && object.range)`，HEAD 和不带 Range 的 GET 一律回 200 + 完整 `content-length`。补测试：不带 Range 的 GET/HEAD 命中 R2 → 200；带 `bytes=0-0`、`bytes=-N` → 206 且 content-range 正确。上线方式沿用现有流程（先 `env.test` 的 cdn-r2-test.makaron.app 验收，再部署生产路由）。这一步不需要动应用，也会同时修好 CLI/MCP/GUI 所有路径。紧急情况下的回滚开关仍是 `R2C_DISABLED=1` 重新部署，但会失去 egress 节省（约 $95–100/月），不建议为此回滚。
2. **应用（防御，随下一次正常发版）**：合入 `ba5cf7ae`，`readProviderImage` 接受“覆盖完整对象的 206”（`content-range: bytes 0-(N-1)/N` 且实收字节 = N）。对 fal/evolink/mule/xai 等第三方域名同样有用。
3. **Retake 交付兜底（建议同批做）**：assembling / saving_patch 阶段的读取失败目前永远是“pending”。建议加重试上限，超过后标记 `failed` 并走 settle 退款，避免“供应商已出片、用户被预留积分卡住”。
4. **上线后验证**：
   - `curl -sI https://cdn.makaron.app/storage/v1/object/public/<已在 R2 的对象>` 连续两次（间隔 > 60 秒）都是 200，`x-makaron-cache: HIT-R2`；带 `Range: bytes=0-0` 是 206。
   - 跑一次真实 `inspect_retake` + `retake_video`（kling-4-flash，短区间）到 `completed`。
   - 复跑 4.1 的 SQL，确认 11-07 以后无新增。
   - 盯 612db792 是否走到 completed/failed。

## 7. 一句话

影响小：上线后 26 小时内 4 次调用、4 个用户、0 扣费、0 退款需求；功能上只影响 Retake 与 fal H3 Max 参考图预检，且是间歇性的。推荐先修 Worker（只在带 Range 时回 206），再随下次发版合入应用侧放宽检查和 Retake 交付兜底。
